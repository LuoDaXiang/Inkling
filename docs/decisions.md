## 0002 — 业务逻辑不写进数据模型

**日期**：2026-08-22
**状态**：已采纳

Enjoy 把业务逻辑写成 Sequelize 模型的静态方法（`Speech.generate()`）。
这些方法直接读 electron-settings、直接调 OpenAI、直接写文件系统、直接建数据库记录。

后果是可测性归零：想测一个函数，必须启动整个 Electron 应用、登录一个用户、
连上数据库、备好真实 API key、发一次真实网络请求。

这就是为什么 Enjoy 的 57,836 行代码只有 6 个测试用例，而且全是 e2e 冒烟测试——
TTS 和评分这两个核心功能一个测试都没有。

**本项目**：模型只管存取。生成逻辑是接受 provider 作为参数的普通函数。

## 0003 — 账号系统不许渗进业务逻辑

**日期**：2026-08-22
**状态**：已采纳

Enjoy 的 TTS 生成逻辑里有这样一段（`enjoy/src/main/db/models/speech.ts:196`）：

```ts
if (engine === "enjoyai") {
  openaiConfig = {
    apiKey: (await UserSetting.accessToken()) as string,
    baseURL: `${settings.apiUrl()}/api/ai`,
  };
} else if (engine === "openai") { ... }
```

「谁付钱」这件事被写进了「怎么合成语音」里。结果是 Enjoy 不登录就不能用。

**本项目**：`Account` 接口只回答两个问题——我是谁（identity）、这次操作准不准且谁付钱（entitlement）。

- `LocalAccount`：我是唯一用户，用自己的 key，永远准。
- `CloudAccount`：服务端说我是谁，服务端扣额度。

Stage 0 到 Stage 3，业务代码一行不改，只换 `Account` 实现。

## 0004 — 音频文件按内容哈希寻址

**日期**：2026-08-22
**状态**：已采纳

这一条抄 Enjoy，它做对了：音频文件存在文件系统上，文件名是内容的哈希，
数据库只存哈希和扩展名，不存 blob。

TTS 要花钱或花算力，所以必须有缓存：先按 `hash(text + engine + model + voice)` 查，
命中就直接返回，不重复生成。

**与 Enjoy 的差别**：Enjoy 的查询键是 `(sourceId, sourceType, section, segment)`，
绑死了业务实体——同一句话出现在两个地方会生成两次。本项目用内容本身做键。

## 0006 — 测试完整性的三条判据

**日期**：2026-08-22
**状态**：已采纳

「测试写够了没有」需要一个可检查的标准，否则永远是凭感觉。本项目用三条：

1. **输入空间被划分完** —— 每一类形态都有至少一个例子，且能说出为什么这些类是穷尽的。
   每个测试文件顶部用注释列出它的分类清单。
2. **每个分支都可达** —— 源码里每个 `if` 都有测试能走到。用覆盖率报告核对，
   不达标的地方要么补测试，要么说明为什么这条分支不该存在。
3. **每种失败都有归属** —— 不是「失败了」，而是「哪一种失败」，每种都有测试，
   且每种的 `retryable` 都被断言过。

三条里最难的是第一条，因为它要求先想清楚问题域。第二条是机械的，
覆盖率工具会告诉你。第三条最容易被跳过，也最容易在线上出事。

**取舍**：不追求 100% 覆盖率。`types.ts` 这类纯类型声明排除在外；
剩下的未覆盖分支必须是有意留下的，不能是忘了写。

## 0007 — 音频只验证结构，不比对内容

**日期**：2026-08-22
**状态**：已采纳

TTS 的输出没有「正确答案」：同一段文字合成两次，字节可能不一样，
换个模型版本音色就变了。所以 `expect(audio).toEqual(expected)` 这种断言写不出来。

做法学微软 Speech SDK（`tests/SpeechSynthesisTests.ts` 的 `CheckRiffPcmComplete`）：
手工解析 WAV 头，逐字段验证 RIFF / WAVE / fmt / PCM 格式码 / data 块，
并检查「头部声明的长度」与「实际字节数」是否一致。

最后那一条是重点，它抓的是**音频被截断**——文件能播放、不报错、只是短了一截。
在跟读场景里表现为评分莫名其妙地低，极难定位。

对于时长这类会波动的数值，断言「相差不超过 10%」而不是相等。

实现见 `src/core/audio/wav.ts`。

## 0008 — 超长文本必须拒绝，不能静默截断

**日期**：2026-08-22
**状态**：已采纳

Kokoro 的分词器上限是 509 token，超出后的处理是 `truncation: true`。
作者自己在源码里留了 TODO（`kokoro.js/src/kokoro.js:143`）：

```js
// TODO: There may be some cases where - even with splitting - the text is too long.
// For now, we just truncate these exceptionally long chunks
```

后果是音频短一截且不报错。而 Kokoro 的分句测试里最长输入只有 157 字符，
中位数 34 字符——**这套测试从来没接近过那个边界**。

本项目的做法：`TtsProvider` 接口带 `maxChars` 字段，`synthesize()` 在调用
provider 之前就检查长度，超出直接抛 `too_long`。宁可报错，不要静默产出坏数据。

## 0009 — 测试分两层，日常那层不联网

**日期**：2026-08-22
**状态**：已采纳

`npm test` —— 纯逻辑，不联网、不写磁盘、不装模型，一秒内跑完，任何人克隆下来就能跑。

这个分层学自 OpenAI 的 node SDK（`scripts/test` 起本地 mock server）
和微软 Speech SDK（`run-connection-tests.sh` 与 `run-non-connection-tests.sh` 分开）。

## 0010 — Azure TTS 走 REST，不用官方 SDK

**日期**：2026-08-22
**状态**：已采纳

Azure 有官方 SDK（`microsoft-cognitiveservices-speech-sdk`），Enjoy 用的就是它。
本项目改用 REST 接口，理由：

1. **零依赖**。Node 自带 fetch，不引入一个几 MB 的包。
2. **错误直接对上已有的分类器**。REST 返回标准 HTTP 状态码，
   `classify()` 已经认得；SDK 会把错误包成 `CancellationDetails`，还要再翻译一层。
3. **fetch 可以注入**。整个 provider 不联网就能测——37 个用例覆盖了
   401/403/415/429/502/503、网络异常、空响应体，这些用真 SDK 根本制造不出来。

**代价**：REST 拿不到词/句边界的时间戳事件，那需要 SDK 的 WebSocket 通道。
我们按句合成、按句缓存，暂时不需要句边界。将来做逐词高亮时再评估是否引入 SDK，
届时只需新增一个实现 `TtsProvider` 的文件，不影响任何已有代码。

接口文档：https://learn.microsoft.com/azure/ai-services/speech-service/rest-text-to-speech

## 0011 — SSML 转义由我们自己负责

**日期**：2026-08-22
**状态**：已采纳

Azure 的 TTS 收的是 SSML（一种 XML），而我们的文本来自用户粘贴或 AI 生成，
两条路径都不可信。文本里的 `<` `>` `&` 轻则让请求变成非法 XML 被 400 拒掉，
重则被当成标记执行：

```
text = '</voice><voice name="zh-CN-XiaoxiaoNeural">被劫持的内容'
```

微软自己的 SDK 测试里，搜 `&amp;` / `escape` / `injection` 全部零命中——
它的 SSML 用例用的是写死的合法 XML。这一层没有现成保障，必须自己守。

`src/providers/tts/ssml.ts` 是纯函数：转义五个 XML 特殊字符、移除 XML 1.0
不允许的控制字符、把音色名解析成语言标记。48 个测试用例，含注入攻击场景。

**顺带**：`maxChars` 默认 3000 是我们自己设的闸门，不是 Azure 的文档限制。
官方只写了「音频超过 10 分钟会被截断」，没给字符数上限。

## 0012 — Stage 0 做本地 Web 应用，Stage 1 才上 Electron

**日期**：2026-08-23
**状态**：已采纳

需求是「macOS 和 Windows 都能用」，最终形态是 Electron 桌面应用。
但 Stage 0 不直接上 Electron，先做本地 Web 应用：浏览器做前端，一个 `node:http` 服务跑在本机。

理由：

1. **Electron 的 renderer 本来就是浏览器。** 界面用标准 Web API 写，
   Stage 1 包进 Electron 时不需要重写，也不需要改 core。
2. **少一整层 IPC。** Electron 的 main/renderer 之间要手写 IPC 通道、preload 桥接、
   再手写一遍类型声明——同一个字段改三处。Enjoy 的 `preload.ts` 有 808 行，
   全是这种胶水。Stage 0 不需要为它付代价。
3. **client/server 边界更真实。** HTTP 是个真边界，逼着我们把「哪些逻辑在服务端」
   想清楚。Stage 2 那台服务器要跑的就是同一份代码。

**关于麦克风权限**：`getUserMedia` 要求安全上下文，而 `http://localhost`
被浏览器算作安全上下文，不需要 HTTPS。

**代价**：Stage 0 期间要手动打开浏览器，没有应用图标，关不掉后台进程时要自己 kill。
这些都是 Stage 1 顺手解决的问题，不值得提前处理。

## 0013 — HTTP 层用 node:http，不引框架

**日期**：2026-08-23
**状态**：已采纳

Stage 0 的服务端只有三个路由：合成、取音频、静态文件。为它引入 Fastify 或 Express
会打破本项目的运行时零依赖（`dependencies: {}`）。

沿用 0010 的同一套理由：Node 自带的东西够用时就不引包。三个路由用 `node:http`
大约 100 行，而且这些代码本身有教学价值——请求解析、状态码、流式响应、
Content-Type，这些是框架替你做掉、但迟早要懂的东西。

**什么时候该改**：路由数量超过六个，或者开始需要中间件、参数校验、
路由参数解析这些东西的时候。那时引框架是划算的，现在不是。

**已经付出的代价**：手写路由没有参数校验，请求体大小限制要自己设，
错误处理要自己兜。这三件事在 `src/http/server.ts` 里都显式做了，没有假装不存在。

## 0014 — live 测试的密钥由 vitest 配置显式注入

**日期**：2026-08-23
**状态**：已采纳

`.env.example` 让人把密钥填进 `.env.local`，live 测试读 `process.env.AZURE_SPEECH_KEY`——
但中间**没有任何东西负责把文件加载进环境变量**。结果是：填好密钥、跑 `npm run test:live`、
仍然是 9 skipped，而且不报错，因为「没配置就跳过」的逻辑无法区分
「用户没配」和「配了但没加载」。

这是一类很坏的 bug：它伪装成正常行为。

**做法**：`vitest.live.config.ts` 自己读 `.env.local` 并通过 `test.env` 显式注入。
零依赖（不用 dotenv），且加载动作发生在配置里，看得见。

**顺带**：live 测试现在会在整组跳过时打印一行原因，而不是静默跳过。
「跳过」和「没配置所以跳过」是两个不同的信息。

## 0015 — 发音评估走 REST，并开启 prosody

**日期**：2026-08-23
**状态**：已采纳（已用真实调用验证）

延续 0010 对 TTS 的同一判断：REST，不引 SDK。运行时依赖保持为空。

**端点与请求形状**（已核实，第一次真实调用即通过）：

```
POST https://{region}.stt.speech.microsoft.com
     /speech/recognition/conversation/cognitiveservices/v1?language=en-US

Ocp-Apim-Subscription-Key: {key}
Content-Type: audio/wav; codecs=audio/pcm; samplerate=16000
Pronunciation-Assessment: {下面这段 JSON 的 base64}
Accept: application/json

{ "ReferenceText": "...", "GradingSystem": "HundredMark",
  "Granularity": "Phoneme", "Dimension": "Comprehensive",
  "EnableProsodyAssessment": "True" }
```

**响应结构与 SDK 不同，这一点会坑人**：REST 原始报文比 SDK 扁一层——
五项分数直接挂在 `NBest[0]` 上（`AccuracyScore` / `FluencyScore` /
`ProsodyScore` / `CompletenessScore` / `PronScore`），**不在
`PronunciationAssessment` 子对象里**。照着 SDK 的字段路径取会全部拿到
`undefined`，而且不报错。第一版测试就是这么写错的。

逐词同理：`Words[i].AccuracyScore` 和 `Words[i].ErrorType` 直接挂在词上。

**实测数据**（TTS 合成的 en-US-AvaNeural，13 词）：

| 场景 | 准确度 | 流利度 | 完整度 | 语调 | 总分 |
| --- | --- | --- | --- | --- | --- |
| 参考文本对上 | 96 | 100 | 100 | 91 | 95.6 |
| 参考文本对不上 | 13 | 0 | 0 | 59.6 | 14.5 |

区分度足够。另外机器给自己合成的语音打 95.6 而不是 100，语调只给 91——
说明它没有盲目偏爱合成语音，这对「用它给人打分」是个好信号。

## 0016 — 逐词语调反馈比总分更有价值

**日期**：2026-08-23
**状态**：已采纳

开启 prosody 之后，响应里每个词还带一个 `Feedback.Prosody`：

```json
{ "Break": { "ErrorTypes": ["None"], "BreakLength": 0,
             "UnexpectedBreak": { "Confidence": ... },
             "MissingBreak": { "Confidence": ... } },
  "Intonation": { "ErrorTypes": [],
                  "Monotone": { "Confidence": 0,
                                "WordPitchSlopeConfidence": 0,
                                "SyllablePitchDeltaConfidence": 0.54 } } }
```

`Monotone` 是单调检测。一个 ProsodyScore 只能告诉用户「语调不太好」，
而 `Monotone.Confidence` 能逐词指出**哪几个词读平了**，`Break` 能指出
**哪里该停没停、哪里不该停却停了**。

跟读训练需要的是后者：知道错在哪，而不是知道自己得了几分。

**因此**：`ScoringProvider` 的返回类型必须保留逐词明细，不能只回五个数字。
M04 建这一层时，数据模型要为 `Words[]` 留位置。

**顺带**：响应还有一个顶层 `SNR`（信噪比，实测 38.7）。将来可以用它
提示「你的麦克风太吵，先换个环境再练」——这是个不用额外成本就能给的提示。

## 0017 — 不抄 Enjoy 的超长音频合并算法

**日期**：2026-08-23
**状态**：已采纳

Enjoy 在 `use-pronunciation-assessments.tsx` 里以 30 秒为界：短音频用
`recognizeOnceAsync`，长音频用连续识别切段后合并。这证实了 30 秒是硬上限。

但它的合并是**等权平均**：1 秒的片段和 20 秒的片段权重相同。
`CompletenessScore` 取平均更是没有意义——完整度衡量的是「参考文本被念了多少」，
把两段的完整度相加除以二不对应任何东西。

**本项目的做法**：不在评分层合并。在**分句阶段**就保证每一句都是可评分单元
（见 roadmap 的 F3），一句一评、一句一分。跟读训练本来就是按句练的，
没有理由把一段三十秒以上的音频当成一个整体去评。

这样既避开了合并的数学问题，也让反馈粒度和练习粒度对齐。

## 0018 — 用 speechocean762 做评分效度测量

**日期**：2026-08-23
**状态**：已采纳（已跑出结果）

**问题**：Azure 给的分数值不值得展示给用户？

原计划是自己录五段音频、凭耳朵排序、看机器同不同意。n=5 的主观印象，
结论不可复现，也说不出「有多准」。

**改用 speechocean762**（Apache 2.0，HuggingFace `mispeech/speechocean762`）：

- 5000 条，train / test 各 2500
- 说话人是母语为普通话的英语学习者，**和本项目目标用户同一人群**
- 每条由 **5 位语言专家独立打分取平均**作为真值
- 维度是 accuracy / fluency / prosodic / completeness / total（0–10），
  **与 Azure 返回的五项一一对应**
- 音频本身就是 16kHz / 单声道 / 16bit，不需要转换
- 时长 1.59–20.4 秒，全部在 30 秒上限内

工具在 `scripts/assessment-validity.ts`，`npm run validity -- --n 150 --min-age 16`。

**先踩了一个坑，值得记住**：第一次按顺序取前 20 个成人，得到的相关系数
全部低于 0.3。看着像「Azure 不准」，其实是**取值范围压扁**——那 20 条的
专家分只有 7/8/9/10 四个取值，completeness 更是全部 10 分、方差为零。
样本在真值上没有差异时，相关系数会被系统性地压向 0。

改成**按专家总分分层抽样**（每个分档取同样多条）之后，结论完全反转。
这条教训比结论本身更值钱：**低相关先怀疑样本，再怀疑被测对象。**

## 0019 — 效度结论：语调可信，完整度不可用，原始分数不可直接展示

**日期**：2026-08-23
**状态**：已采纳

137 条成人样本（16 岁以上），分层覆盖专家总分 3–10 全段：

| 维度 | 皮尔逊 | 斯皮尔曼 | 专家均分 | Azure 均分 |
| --- | --- | --- | --- | --- |
| 准确度 | 0.723 | 0.776 | 65.8 | 85.7 |
| 流利度 | 0.758 | 0.808 | 69.9 | 86.7 |
| **语调** | **0.880** | **0.908** | 66.1 | **66.6** |
| 完整度 | — | — | 100.0 | 86.7 |
| 总分 | 0.815 | 0.869 | 61.2 | 78.3 |

三条产品结论：

**一、语调这一维可以放心做主打。**
0.908 的斯皮尔曼相关是五项里最高的，而且它几乎没有校准偏差
（专家 66.1 对 Azure 66.6）。这正好是参考实现 Enjoy 拿不到的维度
（见 0015）——本项目的差异化不是「做得更好」，是「它没有」。

**二、准确度和流利度系统性偏高约 20 分。**
排序是可信的（0.776 / 0.808），但绝对值不可信。直接展示原始分数会让
用户以为自己比实际水平好得多。

处置：**界面上不展示原始百分数**，改为展示相对变化（「比上次高 4 分」）
和分档（如「接近母语者 / 可懂但有口音 / 需要重练」）。分档的切点用本次
测量的数据反推，而不是拍脑袋定 90/80/70。

**三、完整度这一维不展示。**
专家给的全是 10 分——朗读任务本来就没人漏读，这一维在本场景下没有区分度。
而 Azure 平均只给 86.7，它在惩罚一个专家认为不存在的问题。展示它只会制造
无意义的焦虑。它仍然要存进数据库（成本已经付了，将来可能有用），但不进界面。

**成本**：137 条 ≈ 10.5 分钟音频 ≈ $0.23。

**未做**：`--min-age 16` 筛掉了 1280 条儿童样本。儿童与成人的相关性是否
不同没有测——本项目用户是成人，暂时不需要这个答案。

## 0020 — 发音评估的边缘行为（全部实测，不是推测）

**日期**：2026-08-23
**状态**：已采纳

M04 建 `ScoringProvider` 之前，先把接口的真实脾气摸清。以下每一条都真调过一次。

### 最要命的三条

**一、HTTP 一律 200，失败信息藏在 `RecognitionStatus` 里。**

静音、极短音频、非音频字节，全部返回 **HTTP 200**，但没有 `NBest`。
只看状态码的错误分类器会把「完全没识别到语音」当成成功。

| 输入 | HTTP | RecognitionStatus | NBest |
| --- | --- | --- | --- |
| 纯静音 3 秒 | 200 | `InitialSilenceTimeout` | 无 |
| 0.1 秒静音 | 200 | `InitialSilenceTimeout` | 无 |
| 只有 WAV 头、无采样数据 | 200 | **字段本身不存在** | 无 |
| 非 WAV 的纯文本字节 | 200 | `InitialSilenceTimeout` | 无 |

注意第三行：空数据时**连 `RecognitionStatus` 都没有**。判断顺序必须是
先看 `NBest?.[0]` 存不存在，再谈状态。

**二、参考文本为空时，它照样给高分。**

传空字符串 `""` 作参考文本 → `Success`，准确度 90 / 流利度 100 / 语调 91 / 总分 92.2。
这是无参考（unscripted）评估模式被意外触发了。

**后果**：如果参考文本因为某个 bug 变成空字符串，用户会拿到一个看起来完全
正常的高分，没有任何报错。这是最坏的一类失败——不崩、不报错、结果错。

**必须在送出请求之前拒绝空参考文本**，和 `synthesize()` 拒绝空文本同理。

**三、超长参考文本会让请求挂死，不是报错。**

约 13000 字符的参考文本 → 服务端不返回响应头，`undici` 抛
`UND_ERR_HEADERS_TIMEOUT`。探针脚本就是卡在这里被超时杀掉的。

**必须自己限长，并且给 fetch 设显式超时**。默认没有超时的话，一个坏输入
能把整条请求链挂住。

### 分数的脾气

| 输入 | 准确度 | 流利度 | 语调 | 完整度 | 总分 |
| --- | --- | --- | --- | --- | --- |
| 正常朗读（基准） | 96 | 100 | 91 | 100 | 95.6 |
| **纯白噪声 3 秒** | **71** | 13 | 5.2 | 69 | 32.7 |
| 音频截断到 1/3 | 37 | 100 | **无** | 38 | 49.8 |
| 参考文本为空 | 90 | 100 | 91 | 100 | 92.2 |
| 参考文本只有空格 | 0 | 0 | **无** | 0 | 0 |
| 参考文本是中文 | 0 | 0 | **无** | 0 | 0 |
| 参考比音频多一半 | 67 | 74 | 72.1 | 65 | 68.6 |
| 参考比音频少一半 | **94** | 100 | 91 | **100** | 95.2 |
| 参考含 `< > & "` | 96 | 100 | 91 | 100 | 95.6 |

四条推论：

- **单个维度不能单独信。** 纯白噪声的准确度是 71 分——比及格线还高。
  但流利度 13、语调 5.2、总分 32.7。要判断「这段录音有没有意义」，
  得看组合，不能只看某一项。
- **`ProsodyScore` 会缺席。** 音频截断、参考无效时它直接不出现。
  取值必须当 `number | undefined` 处理。
- **多读不扣分。** 参考只有音频内容的一半时，分数几乎不降（95.2）。
  完整度衡量的是「参考里的词你念了多少」，不是「你有没有念多余的」。
  用户读错成另一句更长的话，仍然可能拿高分。
- **`ProsodyScore` 从不给 100。** 迄今所有实测最高 91.1。界面若按
  「满分即完美」设计进度条，语调那条永远填不满。

### 一条更正

此前我判断「采样率声明不符会静默压低分数」，**这是错的**。
实测 24kHz 音频无论 `Content-Type` 里声明 16000 还是 24000，
五项分数完全一致（96/100/91/100/95.6）——**Azure 读 WAV 头，忽略声明**。

格式强校验仍然要做，但理由不再是「防止静默降分」，而是：
- 提前拒绝比让服务端猜更可预测
- 送 44.1kHz 立体声上去是白白多花带宽和钱

### 未测

- 超过 30 秒的音频（实测 137 条最长 11.4 秒，正常朗读碰不到；
  用户导入长文本时才会碰到，M04 拆句解决）
- 429 限流的 `Retry-After` 头（效度脚本里写了指数退避，但没真撞上过）
- 立体声、8-bit、非 PCM 编码

## 0021 — 语调评分的适用范围：擅长挑出差的，分不出好和更好

**日期**：2026-08-23
**状态**：已采纳

137 条真人样本，专家语调分对 Azure `ProsodyScore` 的响应：

| 专家分 | 样本 | Azure 均值 | Azure 范围 |
| --- | --- | --- | --- |
| 3 | 3 | 22.5 | 13–34 |
| 4 | 18 | 36.3 | 23–56 |
| 5 | 23 | 54.5 | 34–73 |
| 6 | 25 | 63.5 | 27–82 |
| 7 | 23 | 72.7 | 61–84 |
| 8 | 13 | 84.7 | 77–91 |
| 9 | 26 | 86.9 | 78–91 |
| 10 | 6 | 88.6 | 83–91 |

单调递增，3 分到 7 分之间每档拉开约 10 分，区分度很好。

**但 8/9/10 三档压在 84.7 / 86.9 / 88.6**，只差 4 分，而各档内部范围都到 91。
也就是说：**它能可靠地告诉你「读得不好」，但分不出「好」和「很好」。**

界面上高分段不要再显示细微差别，改成一个「已达标」状态即可，
把注意力引导到逐词的 `Monotone` / `Break` 明细上。

**另一个佐证**：本项目 TTS 合成音的 `ProsodyScore` 稳定在 88–91，
落在专家 9–10 分档。这也意味着 **Azure TTS 造不出「读得平」的样本**——
用 SSML 的 `contour` 压平音高，合成出的音频字节与默认完全相同（SSML 被忽略），
`mstts:express-as` 的 `cheerful` 在 `en-US-AvaNeural` 上同样无效。

所以受控语调实验这条路走不通，好在真实数据集已经把这个问题答完了。

## 0022 — 超长音频会被静默截断，必须在送出前拦

**日期**：2026-08-23
**状态**：已采纳（实测）

此前多处写着「单次评分音频不超过 30 秒」，来源是文档和参考实现 Enjoy 里的
`THIRTY_SECONDS` 阈值。**这条断言从没验证过，而且性质说错了。**

实测（同一句话重复拼接，TTS 合成）：

| 时长 | HTTP | RecognitionStatus | 完整度 | 总分 |
| --- | --- | --- | --- | --- |
| 18.4 秒 | 200 | Success | 100 | 94.5 |
| 36.6 秒 | 200 | Success | 96 | 91.4 |
| 73.3 秒 | 200 | Success | **49** | 65.7 |

**不是硬拒绝，是静默截断。** 73.3 秒的完整度 49 ≈ 35/73.3，36.6 秒的
96 ≈ 35/36.6——两个数都指向「只处理了前 35 秒左右」。

后果比硬拒绝坏得多：用户完整读完一大段，看到「完整度 49」，会以为自己
漏读了一半。没有报错、没有警告、状态是 Success。

这正是 0007 和 0008 反复强调要防的那类失败——**能跑、不报错、结果错**。

**处置**：`assertAssessable()` 在 `core/audio/wav.ts`，上限取 30 秒
（比实测的 ~35 秒留余量），超限直接抛。M04 的评分 provider 必须调它。

## 0024 — parseWav 此前只认 44 字节固定头，比 Azure 严格

**日期**：2026-08-23
**状态**：已修复

RIFF 是块结构，不是固定布局。`fmt ` 和 `data` 之间可以插任意多个块：

- **ffmpeg 会插 `LIST INFO`**（写入编码器版本号）
- 压缩格式会插 `fact`
- `fmt ` 块本身可能是 18 或 40 字节而不是 16（带 `cbSize` 或 EXTENSIBLE）

原实现按「`data` 一定在偏移 36、音频数据一定从 44 开始」硬读，以上三种
**合法 WAV 一概拒收**——而 Azure 照单全收。

没被发现的原因：我们自己的 Azure TTS 和 speechocean762 数据集恰好都产
干净的 44 字节头。321 个用例 + 137 条真实样本全部漏过。**测试数据和生产
数据同源时，这类 bug 一定漏。**

**已改为块遍历**，并保留原有的截断检测（那一条很有价值）。
块长度为奇数时按 RIFF 规范跳过填充字节。

顺带：新增的 4 个用例第一次跑也失败了，查下来是**测试样本自己没补填充
字节**，解析器是对的。写测试数据同样会出 bug。

## 0025 — 请求体上限按路由分开

**日期**：2026-08-23
**状态**：已修复（预防性）

`MAX_BODY_BYTES = 64 * 1024` 是 M01 写的，当时脑子里想的是 JSON 请求体。

但 16kHz 单声道 16bit 音频是 **32,000 字节/秒**，64KB 只够 **2.0 秒**。
M03 一上传录音，**任何超过两秒的录音都会被自己的服务器拒掉**，
而错误信息只会说「请求体过大」，看不出真正的原因。

这个 bug 当时没有任何测试能发现——录音路由还不存在。它是**跨里程碑的**：
在 M01 写下，到 M03 才引爆。

已拆成 `MAX_JSON_BYTES`（64KB）和 `MAX_AUDIO_BYTES`（1MB，容得下 30 秒），
`readBody()` 改为显式接收上限，调用方必须自己指明用哪个。

## 0026 — 测试完整性再加两条判据（修订 0006）

**日期**：2026-08-23
**状态**：已采纳

0006 定了三条判据。这一轮修 `parseWav` 和请求体上限两个 bug 时发现，
那三条**都满足了，bug 还是漏了**。所以补两条。

### 四、测试数据不能和生产数据同源

`parseWav` 只认 44 字节固定头，凡是 ffmpeg 转出来的文件（带 `LIST INFO` 块）
一概拒收——而 Azure 照单全收。321 个用例全绿。

漏掉的原因：测试样本用 `buildWav()` 造，生产音频来自 Azure TTS，
**两者恰好都产干净的 44 字节头**。输入空间在纸面上划分完了，
但每一类里塞的都是同一个模子刻出来的样本。

**做法**：每个解析器至少要有一组**不是我们自己生成的**样本。
拿不到真实样本时，手工构造对抗性样本，并在注释里写明它模仿的是谁的产物。

`scoring-parse.test.ts` 的 `REAL` 常量就是这么来的——从一次真实响应剪下来的，
不是照着类型定义编的。

### 五、跨层约束要有整条链的断言

`MAX_BODY_BYTES = 64 * 1024` 是 M01 写的，当时想的是 JSON。
但 16kHz 单声道音频是 32,000 字节/秒，64KB 只够 2 秒。M03 一上传录音就炸。

**任何单层的测试都抓不到它**：HTTP 层的测试只知道「超过上限要拒绝」，
音频层的测试只知道「30 秒是上限」，没人把两个数字放在一起算过。

**做法**：凡是一个约束跨越两个模块，就写一条把整条链算出来的测试。
形如「30 秒音频 → 多少字节 → 是否在请求体上限内」，让数字自己对账，
而不是靠人记得两处要同步改。

### 这两条和前三条的关系

前三条管**覆盖**：输入空间划分完、分支都可达、失败都有归属。
后两条管**样本质量**和**跨层一致性**——覆盖率再高，如果每一类里的样本
都长得一样，或者两个模块各自自洽但拼不起来，测试仍然是绿的而系统是坏的。

## 0027 — 评分结果分三种走向，不是「成功或失败」

**日期**：2026-08-24
**状态**：已采纳

`assess()` 返回一个可辨识联合，而不是「返回结果或抛错」：

```ts
type AssessOutcome =
  | { kind: "scored"; result: AssessmentResult }
  | { kind: "unreliable"; result: AssessmentResult }
  | { kind: "no_speech" };
```

理由是这三种在**界面上是三种完全不同的呈现**：

- `scored` —— 显示分数与逐词明细
- `unreliable` —— 显示「听起来像是环境噪声」，并附上信噪比。
  **结果仍然带回来**，丢掉的话这个提示就没素材了
- `no_speech` —— 显示「没有听到声音，检查一下麦克风」

如果压缩成「成功 / 失败」两种，`no_speech` 只能抛错，而界面会显示
「出错了」——可实际上系统工作正常，是用户录了一段没有语音的东西。
**让用户为系统的正常行为感到困惑，是最容易犯又最难发现的设计错误。**

`unreliable` 的判据来自实测：纯白噪声的准确度是 **71 分**，比及格线还高，
只看那一项会把噪声当成「读得还行」。所以看流利度和总分的组合。

**边界用真实数据定，不是拍的**：

| 输入 | 分数 | 判定 |
| --- | --- | --- |
| 纯白噪声 | 准 71 / 流 13 / 总 32.7 | `unreliable` |
| 专家给 3 分的真人样本 | 总分 40.8 / 语调 27.1 | **`scored`** |

读得差的人最需要反馈，判成不可信等于把最该帮的人拒之门外。

**顺带**：测试里有一条穷尽性用例，将来加第四种走向时它会编译失败，
提醒所有调用方跟着改。

## 0028 — 评分有重试，TTS 没有

**日期**：2026-08-24
**状态**：已采纳

同一个仓库里两个编排层，一个重试一个不重试。理由不是疏漏：

**TTS 失败**，用户再点一次按钮就行，代价只是等待几秒。
**评分失败**，意味着**那一遍朗读白读了**——用户得重新录一遍，
而重录的那一遍和刚才那遍不是同一个表现，历史曲线上就少了一个点。

所以 `assess()` 对可重试的失败自动重试（默认 3 次请求，500ms 起指数退避），
`synthesize()` 不重试。

**判据三在这里的落法**：不可重试的六种分类每个都断言了「只请求了一次」。
只断言「抛错」的话，「auth 被重试到额度耗尽」这种 bug 测不出来——
拿着一个错密钥重试，每次都失败，每次都计费。

## 0029 — 不可达代码不写说明，直接消灭

**日期**：2026-08-24
**状态**：已采纳

判据二说「未覆盖的分支要么补测试，要么说明为什么这条分支不该存在」。
写 `assess()` 时遇到一个：

```ts
for (let attempt = 0; attempt <= maxRetries; attempt++) { ... }
// 循环必然在内部返回或抛出，这里只是让类型收敛
throw toServiceError(lastError, ...);
```

最后那行永远走不到。当时的处置是给它写一行说明——**这个处置是错的**。

**不可达代码写不出测试，也就没有东西能保证它是对的。** 它会在重构时
被改坏而没人发现，还会误导后人以为存在某条真实路径。

改用没有终止条件的循环（`for (let attempt = 0; ; attempt++)`），
每条路径都以 `return` 或 `throw` 结束，类型自然收敛，那一行消失了。

**规则收紧为**：优先消灭，其次补测试，「写说明」只留给真正外部约束
导致的不可达（比如平台差异分支）。

## 0030 — 参考 Enjoy 的录音实现：抄三条，避三条

**日期**：2026-08-24
**状态**：已采纳（M03 动手前的调研结论）

**先说测试**：Enjoy 的录音功能**零测试**——e2e 里连 `record` 这个词
都没出现。这某种程度上是诚实的，录音确实依赖麦克风和浏览器实现；
但它把**能测的部分**（格式转换、静音修剪、时长计算）也一起放弃了。
原因是它的录音逻辑散在 provider、组件、主进程模型三处，每处都混着
IPC 和文件系统，**一个测试都写不了**。

**它的链路**：

```
第三方库录音 → Blob（WebM/Opus）→ IPC → echogarden 解码
→ 掐首尾静音 → 编码 WAV → 落盘 → ffmpeg 转 mp3 存起来
→ 评分前再 transcode 回 16kHz WAV
```

### 抄这三条

1. **录音配置 `sampleRate: 16000, sampleSize: 16`**——和我们已定的一致。
2. **掐掉首尾静音再落盘**（`trimAudioStart` -50dB / `trimAudioEnd` -100dB）。
   这条我原先没想到，很有价值：用户点「录音」到开口总有一两秒空白，
   **这段静音会拉低流利度分数，而它和发音水平毫无关系**。
   开头阈值比结尾宽松，因为一开口就有声音，结尾要等确认真的没声了。
3. **到点自动停止**。它按类型分 1 分钟 / 10 分钟；我们的上限是 30 秒。

### 避这三条

1. **不存 mp3。** 它的链路是 WebM → WAV → mp3 → WAV，**两次有损转换**。
   我们直接存 16kHz WAV，磁盘多占一点，换来的是转码损失不影响分数。
2. **不引第三方录音库。** `react-audio-voice-recorder` 产出的是浏览器
   默认格式（WebM/Opus），**Azure 不收**——Enjoy 必须再靠 echogarden
   转码才能用，等于为了一个库引入了另一个更重的库。
   我们用 AudioWorklet 直接取 16kHz PCM，**源头就是对的格式，
   转码这一步整个消失**。
3. **不引 echogarden / ffmpeg-static**（加起来上百 MB）。它需要这些是因为
   要处理 YouTube、播客等任意来源的音频；我们只处理自己录的音。

### 分层纪律

```
core/audio/encode-wav.ts     Int16Array → WAV 字节   纯函数，可测
core/audio/trim-silence.ts   掐首尾静音              纯函数，可测
public/recorder.js           AudioWorklet + 权限      不可测，尽量薄
```

**浏览器那层只负责「拿到采样」，别的什么都不做。** 拿到 Float32 之后
立刻交给纯函数——转 Int16、掐静音、拼 WAV 头，三步全在 `core/`。

这正是 Enjoy 做不到的：把不可测的部分压到最薄，其余全部可测。

## 0031 — Stage 0 不支持 Firefox

**日期**：2026-08-24
**状态**：已采纳

我此前在路线图里写过「用 `new AudioContext({sampleRate: 16000})`，
重采样这一步整个消失」。**这句话在 Firefox 上不成立。**

已核实：Firefox 会报 `AudioContext.createMediaStreamSource: Connecting
AudioNodes from AudioContexts with different sample-rate is currently not
supported`，并且**忽略 `getUserMedia` 的 `sampleRate` 约束**。

**处置**：Stage 0 明确不支持 Firefox，检测到就告知用户换 Chrome 或 Safari。

理由是加重采样要多花约 4 小时，而它只服务一个浏览器；而且重采样本身
会引入音质损失，可能影响评分——那是这个产品的核心。

**防线不止一道**：除了检测 userAgent，还在建完 `AudioContext` 之后
断言 `context.sampleRate === 16000`。浏览器可能不理会这个请求，
而不一致会让编出来的 WAV 时长和实际对不上，评分随之出错——
**这类不一致不会报错，只会让分数悄悄不对**。

将来要支持 Firefox 的话，加一个重采样模块即可，接口不用改。

## 0032 — 浏览器只发原始采样，转换在服务端

**日期**：2026-08-24
**状态**：已采纳

`POST /api/assess` 的请求体是**原始 Float32 采样**，不是编码好的 WAV。

理由：格式转换、静音修剪、WAV 编码这三步都是纯逻辑，放在服务端就有
171 个用例覆盖；放在浏览器端就一个都测不了。**浏览器层因此可以做到
零业务逻辑**——而它恰恰是唯一测不了的一层。

代价是上传体积翻倍：Float32 每采样 4 字节，30 秒 16kHz 是 1,920,000 字节。
所以 `MAX_PCM_BYTES` 必须是 `MAX_AUDIO_BYTES` 的两倍多。
这两个数字的关系有对账测试守着（判据五）。

**对照参考实现**：它的链路是浏览器录 WebM/Opus → IPC 送主进程 →
解码 → 修剪 → 编码 WAV → 转 mp3 存 → 评分前再转回 WAV，
**两次有损转换**，而且逻辑散在三个文件里、混着 IPC 和文件系统，
所以它的录音功能一个测试都没有。

## 0033 — 静音修剪不能用均方根

**日期**：2026-08-24
**状态**：已采纳（测试抓出来的）

第一版按窗口的均方根能量判断「有没有人在说话」。测试用例里放了一个
孤立的爆音采样（模拟录音开头的电流声），修剪直接失效。

算了一下：一个 30000 的爆音落在 160 采样的窗口里，
RMS = √(30000² / 160) ≈ 2371，是阈值 103 的 **23 倍**。
**平方会放大离群值**，所以单次咔哒声足以骗过 RMS。

改成按**占比**判断：窗口内超过阈值的采样占多大比例。
一个爆音只占 1/160 ≈ 0.6%，正弦语音占 99%，轻辅音占 88%。
20% 这条线把两者分得很开。

**这个缺陷是测试抓出来的，不是想出来的。** 我在上一轮列边缘情况清单时
写的是「用窗口而不是单点」——方向对，但没意识到窗口内用什么统计量
同样关键。

**另外三个参考实现照抄不得的地方**：

1. 它结尾用 **-100 dBFS**，换算成 16 位整数是 **0.33 个量化单位**——
   低于 1，意味着「恰好为 0」。任何底噪都掐不动，那一半等于白做。
   我们两端都用 -50 dBFS（约 104），那是个真实的底噪高度。
2. **起音余量**：p / t / k 的起音是陡峭瞬态。切在阈值交越点会削掉
   前沿，听感变闷、**准确度分数下降**。所以往前退 50ms。
3. **直流偏置**：有些麦克风的静音段绝对值恒定不为零。不去均值的话
   修剪完全失效——而且不报错。

## 0034 — 请求体超限时不能 destroy 请求

**日期**：2026-08-24
**状态**：已修复（测试抓出来的）

`readBody` 在超限时调用 `req.destroy()`，**那会在响应发出之前掐断连接**。
客户端拿到的是连接重置，看到的错误是「fetch failed」，
完全不知道是自己传太大了。

正确做法是：停止累积、立刻清空已收到的字节释放内存、拒绝 Promise，
让上层把 413 正常发出去，剩余字节自然丢弃。

**这个 bug 在 JSON 那条路上一直存在**（M01 就写下了），
从来没被测到——因为没有人真的用一个超大请求体打过它。
写录音路由的 413 用例时才暴露出来。

又是判据四的形态：**没有真正制造过这个输入，就等于没测过这条路径。**

## 0035 — 准确度是主打维度，流利度与语调是辅助

**日期**：2026-08-24
**状态**：已采纳（推翻 0019 与 0021 的产品定位部分）

**说话首先要说准。** 音念错了，再流利、语调再自然也是错的；
音念准了，流利和语调才是在这之上的加分项。

此前 0019 写的是「语调可以做主打」，理由是它的相关系数最高（0.908）、
校准偏差最小。**那个理由混淆了两件事**：

- **测得准不准**——是评分服务的属性
- **值不值得当主打**——是产品判断

语调的测量质量最好，这个事实不变；但测得最准的维度不等于最该突出的维度。
一个能精确告诉你「语调略平」却不告诉你「这三个音念错了」的产品，
把用户的注意力引到了次要的地方。

### 这个改动让「不展示原始百分数」更要紧，不是更宽松

效度测量的数据：

| 维度 | 斯皮尔曼相关 | 专家均分 | 服务端均分 | 偏差 |
| --- | --- | --- | --- | --- |
| **准确度** | 0.776 | 65.8 | 85.7 | **+19.9** |
| 流利度 | 0.808 | 69.9 | 86.7 | +16.8 |
| 语调 | 0.908 | 66.1 | 66.6 | +0.5 |

准确度的**排序**是可信的（0.776 属于强相关，足以支撑趋势曲线和
「这次比上次好吗」），但**绝对值虚高约 20 分**。

主打维度报一个虚高的数字，整个产品的可信度就没了——用户以为自己
念得很准，实际不是。所以 0019 定的「只展示分档不展示原始百分数」
这条规则**因为这次改动而更加必须遵守**，分档切点仍用效度数据反推。

### 界面上的落法

1. **准确度排第一并高亮**，流利度次之，语调第三。
2. **逐词标记有优先级**：念错了（红）盖过读得平（黄）。一个词两样都占时
   先报念错——把音念对是基础。
3. **文案先说准确度的问题，再说语调**。顺序反过来会让用户去调语调，
   而真正该改的是那几个念错的音。
4. **悬停显示音素级明细**。「第 3 个词念错了」不够，
   「第 3 个词的 /θ/ 念成了 /s/」才是能拿去改的东西。

### 语调仍然保留，理由变了

不再是「主打」，而是两条：

- **它是竞品缺口**。参考实现 Enjoy 从没调用 `enableProsodyAssessment`，
  它数据库里的 `prosodyScore` 那一列永远是空的（见 0015）。
  我们有，是差异化，但差异化不等于主打。
- **它测得最准**，所以适合放在趋势曲线上看长期变化——
  准确度改善需要几周，语调的变化在几天内就能看出来。

`en-US` 的硬性限制照旧：换区域设置会让语调分静默缺席，
而静默降级比报错糟糕。理由从「它是主打」改成「静默缺席的东西
一律不许存在」——那是个更普适的规则。

### 未变的部分

0019 的另外两条不受影响：**完整度不展示**（朗读场景专家全给满分，
没有区分度），**语调分擅长挑出差的、分不出好和更好**（8/9/10 三档
只差 4 分，高分段不该显示细微差别）。

## 0037 — SQLite 的连接约定

**日期**：2026-08-25
**状态**：已采纳

SQLite 有几个反直觉的默认值，而且失败方式**全是静默的**——不报错，
只是行为和你以为的不一样。所以每一条都必须显式设，并且有测试盯着。

`src/storage/db.ts` 的 `configure()` 里四条 pragma，**顺序不能动**：

```
PRAGMA auto_vacuum = INCREMENTAL   ← 必须第一
PRAGMA journal_mode = WAL          ← 只对文件库
PRAGMA busy_timeout = 5000
PRAGMA foreign_keys = ON
```

### 为什么 auto_vacuum 必须排在 WAL 前面

第一版写反了，实测才发现：

```
PRAGMA journal_mode=WAL; PRAGMA auto_vacuum=INCREMENTAL;  -> 0  ✗
PRAGMA auto_vacuum=INCREMENTAL; PRAGMA journal_mode=WAL;  -> 2  ✓
```

切换到 WAL 会写数据库头，而 `auto_vacuum` 就存在头里——头一旦写下，
`auto_vacuum` 被焊成 0，之后再设**不报错、读回来还是 0**。

而且它只在**建任何表之前**有机会生效。错过了要补救就得停服跑一次
全库 `VACUUM`（独占锁 + 额外的等大磁盘空间）。

不设的后果实测过：删掉 4000 行流水，`.db` 文件大小**一个字节都不变**——
DELETE 只是把页挂到 freelist 上。有了 INCREMENTAL 才能在 `prune()` 之后
在线跑 `incremental_vacuum` 回收。

选 INCREMENTAL 不选 FULL：FULL 在每次提交都回收，给写入路径加税；
流水的写入在请求路径上，不能为了回收空间给每次写加成本。

### 其余三条

- **WAL**：默认的 rollback journal 模式下写者会把读者一起挡住。内存库设了不生效，
  所以**并发相关的测试必须用真实临时文件**。
- **busy_timeout**：是**每连接**属性，不写进数据库文件，新开一个连接就得重设。
  有测试专门盯着这一点。
- **foreign_keys**：原生 SQLite 默认不强制，约束被解析但不执行，形同注释。
  `node:sqlite` 帮我们默认打开了，但那是它的选择不是 SQLite 的，所以仍然显式设。

### 建表一律加 STRICT

少了它，`INTEGER` 列能存 `'wxyz'` 而不报错——类型写错不在写入时暴露，
要等到读出来才炸。有一条测试遍历 `sqlite_master`，任何一张表少了 STRICT 就红。

### 备份不能只拷 .db

开了 WAL 之后最近的事务在 `.db-wal` 里，只拷主文件会得到一个丢了最近
记录的库。用 `VACUUM INTO` 产出完整、紧凑、一致的副本。

## 0038 — 操作流水的三条硬约束

**日期**：2026-08-25
**状态**：已采纳

`operations` 表每次调用外部服务记一行。超时和限流这两类故障的共同点是
**不可复现**——用户说「卡住了」，本地跑一百遍都正常。没有流水，
手上就只有那一句「卡住了」。

### 一、写流水永远不抛异常

它是可观测性设施，不是业务主路径。流水自己挂了不能把评分请求一起带走——
那是本末倒置：**最需要记录的时刻，恰恰是最容易出错的时刻**。

`append()` 内部全包在 try 里，失败返回 `false`。但「不抛」不等于「不报」——
失败走 `onError` 回调，生产环境接到 console.error 上。流水静默失效是
最坏的情况：你以为有记录，出事时才发现什么都没有。

`ServerDeps.log` 做成**可选**，路由用 `deps.log?.append()`。类型签名本身
就是这条契约的第一道保证。契约在存储层和 HTTP 层各验一次——路由里
只要有一个地方 await 了它、或者把它放进了 try 之外，契约就破了。

### 二、排序靠 id，不靠 ts

`Date.now()` 不单调：NTP 校时会让它往回跳，同一毫秒内多条记录的先后
也无从分辨。而「先重试还是先失败」恰恰是排查的关键。

`id` 是 rowid，单调递增。`ts` 只用于展示和时间范围查询，**两个用途不能混**。
有一条测试把时钟往回拨 5 秒再写，断言回放顺序仍然正确。

### 三、meta 只收白名单里的键

请求上下文里混着 subscription key，一个顺手的 `JSON.stringify(request)`
就把密钥写进了库。用户读的句子（`reference`）和识别结果（`recognized`）
是语音内容，属于 PII，同样不能进。

白名单是唯一可靠的做法——黑名单永远漏。不在名单里的键**静默丢弃**，
不报错（报错会违反第一条）。字符串值截断到 512 字符：Azure 挂掉时会
返回整页 HTML，不截断就整页进库。

### append-only 用触发器焊死

`BEFORE UPDATE` 触发器 `RAISE(ABORT)`，写下去的事实不允许改口。
`DELETE` 放行——保留策略要靠它裁剪老记录。

流水表**不挂任何外键**：它要能比业务数据活得久。有测试盯着
`operations` 的建表语句里不出现 `REFERENCES`。

## 0040 — 音频缓存必须原子写入

**日期**：2026-08-25
**状态**：已修复（三个「可以缓一缓」的缺口叠出来的正确性 bug）

`FileAudioStore.put()` 原先直接 `writeFile(path, audio)`。三个各自被
归档为低优先级的缺口，组合起来是一个谁都没描述的永久损坏：

```
F4 无 in-flight 去重
  → 两个并发的相同请求，各调一次 provider
  → 缓存键是**请求哈希**不是内容哈希（见 0004），两段音频不保证逐字节相同
  → 并发 writeFile 到同一路径（先截断再写）→ 交错 → 坏 WAV
get() 只 stat 不校验内容
  → 坏文件被当成缓存命中
F8 无淘汰
  → 永远不会被替换掉
```

用户看到的是某一句话的音频永远是坏的，重启没用，也没有任何界面能清掉它。
第二条触发路径是磁盘满：写到一半 ENOSPC，截断的文件留在那里。

改成写 `${path}.${uuid}.tmp` 再 `rename()`。同目录内的 rename 在 POSIX 上
是原子的：要么看到完整的旧文件，要么看到完整的新文件，不存在中间态。
临时文件带随机后缀，并发的两个写者不会互相踩；失败时 unlink 收走。

**F4 的归类因此要改。** 它原先写的是「并发相同请求付两次钱」，归在 M07——
按成本问题排的。但在 `put()` 修好之前，它同时是数据损坏的触发器。
修好之后 F4 才真的只剩重复付费。

验证方式：把修复临时撤回，三条并发用例立刻变红。测试抓不到 bug 就是摆设。

## 0041 — 流水记录花费：微元、向上取整、只在成功且未命中缓存时记

**日期**：2026-08-25
**状态**：已采纳（F13）

`operations.cost_micros` 之前一直是空的——列建了，但没有任何路由传过它，
`summary().costMicros` 在生产环境永远返回 0。

### 单位是微元，且必须是整数

微元 = 百万分之一美元。用整数不用浮点，因为花费要累加，
而浮点累加会漂——一年几万次调用之后总额和账单对不上。
有一条测试累加一万次小额调用，断言结果是精确整数。

### 费率不写死在代码里

`src/core/cost.ts` 只做换算，不知道费率是多少；费率从环境变量注入
（`TTS_MICROS_PER_MILLION_CHARS` / `SCORING_MICROS_PER_AUDIO_HOUR`）。

理由：费率随 Azure 的定价层级、区域和具体合同变化，**写死的费率一定会过期，
而且过期时不报错**。填了但不是合法非负数时启动直接退出，不静默忽略——
一个悄悄变成 `undefined` 的费率会让成本报表永远是 0，而那看起来一切正常。

### 没配费率记 null，不记 0

「没配费率，不知道」和「确实免费」必须分得开。把没配置记成 0，
成本报表会一切正常，直到收到账单。

### 向上取整

系统性向下取整会让「很多次很便宜的调用」总额显著偏低，而成本数据的用途
是决策（还要不要继续用这家、要不要加缓存）。偏低的估算会让决策偏向「再撑撑」。
宁可估高一点点。

### 三种不计费的情形

| 情形 | 为什么 |
| --- | --- |
| **缓存命中** | 没调外部服务。这是 TTS 缓存存在的全部理由，必须能在流水里看出来 |
| **失败** | 401 / 429 / 网络断都没有产生可计费用量。算进去会让成本看起来比实际高 |
| **修剪后什么都不剩** | 整段静音，根本没走到调用那一步 |

反过来：服务返回「没识别到语音」**要计费**——音频确实送出去了。
这两条在代码里只隔十几行，各有一条测试。

### 评分按修剪后的时长计费

不是用户按住录音键的时长。首尾静音被掐掉了，那部分没有送出去。
直接用上传的采样数会把静音也算进账单——这是最容易记错的一条，
有一条测试上传 5 秒、实际评约 2 秒，断言花费对应的是后者。

### 一个已知的不精确

`assess()` 带重试，但 `AssessOutcome` 不携带尝试次数，所以重试后成功
只记一次花费。这**大概率是对的**——失败的尝试通常不计费——但
**没有拿真实账单核对过**，已记入 roadmap 的未核实清单。

## 0042 — 流水按 service 拆分 TTS 与评分

**日期**：2026-08-25
**状态**：已采纳（F14，迁移 v3）

roadmap 的验收标准是「能查出上周练了几次、失败几次、花了多少」。
第一问之前答错了：`summary()` 数的是 `kind='request'` 的总行数，
**TTS 合成和发音评分混在同一个计数里**。听一次范本再跟读一次会记 2，
但那是 1 次练习。

靠 `provider` 区分不了——两边都是 `'azure'`。所以走迁移 v3 加一列
`service TEXT`（`'tts' | 'scoring'`），`summary(from, to, service?)` 按它过滤。

「练了几次」= `summary(a, b, 'scoring').requests`。

### 老行是 NULL，且不算进任何一侧

v3 之前的记录我们**确实不知道**属于哪一侧。加非空列并填一个默认值
就是伪造历史（Atlas 的 MY101 / MF103 检查的正是这个）。

所以：带 service 过滤时老行两边都不计入，不带过滤时仍计入总数。
有一条测试专门盯着这个语义——它容易被「顺手把 NULL 归到某一侧」改坏。

## 0043 — 原子写抽成共享函数，录音 store 独立成类

**日期**：2026-08-26
**状态**：已采纳（契约落地第 4 步）

契约 §12 要求「新增录音音频 store，**不复用 `FileAudioStore`**」。理由是
键语义相反：`FileAudioStore` 的键是请求参数派生的，去重是目的；
录音同一句录十次是十份必须各自保留的音频，去重就是数据丢失。

但直接照做会产生第二份 temp + rename 的实现——**而那正是 F15 那个坑的形状**。
0040 的教训不是「某个文件写错了」，是「直接写目标路径」这个做法本身
会产生永久损坏，所以它不该有第二份实现。

解法是把原子写抽成 `storage/atomic-write.ts` 的 `writeFileAtomic()`，
两个 store 各自调用它。这样：

- 满足 §12：`RecordingStore` 不是 `AudioStore`，接口不同（`put` 不吃键，
  键由内容决定），语义独立
- 不重复：原子写只有一份实现，将来要改（比如加 fsync）只改一处

**键用内容哈希**（对编码后的 WAV 取 sha256）。两段逐字节相同的音频会共用
一个文件——对真实录音这实际上不会发生（麦克风底噪保证每次都不同），
而万一发生了，共用也是对的：它们本来就是同一串字节。
这和「按请求去重」是两回事。

**独立目录还有第二个理由**：F8 将来要给 TTS 缓存加淘汰策略。
混在一个目录里，淘汰会把用户的录音一起删掉——那是用户资产，不是缓存。

## 0045 — 逐词标记是三层叠加，不是查表

**日期**：2026-08-29
**状态**：已采纳（迁移 M2.1）

参考实现的 `pronunciation-assessment-word-result.tsx:42` 是一个查表：

```tsx
const WordDisplay = {
  None: …, Mispronunciation: …, Omission: …, Insertion: …,
  UnexpectedBreak: …, MissingBreak: …, Monotone: …,
}[result.pronunciationAssessment.errorType];
```

**一个词只能显示一种错误**，因为 Azure 的 `errorType` 是单值枚举。
Inkling 的 `WordScore` 不是——它是**三个正交字段**：

```ts
errorType:   WordErrorType;                  // 单值
monotone?:   number;                         // 0–1 连续值，独立字段
breakError?: "unexpected" | "missing";       // 独立字段
```

一个词可以同时「念错了」和「读平了」。查表结构表达不了这件事，
所以不复用它的组件，数据结构从 `WordScore` 重新长。

### 三层，各自管一个字段

| 层 | 视觉 | 取自 | 说明 |
| --- | --- | --- | --- |
| 底色 | 背景色 | `errorType` + `accuracy` | 念错 / 漏读 / 多读 / 正常 |
| 次级 | 下划线粗细（三档） | `monotone` 的 0–1 强度 | 连续量映射成三档，不是布尔 |
| 第三层 | 词尾 / 词间的小标记 | `breakError` | 该停没停、不该停却停了 |

**一个词同时念错且读平时，底色必须是念错**（沿用 0035 第 2 条：
把音念对是基础，语调是在这之上的事）。但**读平的下划线照样画**——
优先级说的是「底色归谁」，不是「其余的层不显示」。查表结构做不到的
恰恰是这一点。

### 韵律类的 errorType 归到它对应的那一层，不进底色

`Monotone` / `UnexpectedBreak` / `MissingBreak` 三个取值虽然长在
`errorType` 这个字段上，但它们描述的是韵律，不是发音。把它们涂成
「念错了」的底色，用户会去改一个根本没念错的音。

所以：这三个取值**不设底色**，各自折进第二、第三层。
将来接一个只给单值枚举的 provider 时，这条映射保证它的输出仍然落在
正确的层上，而不是被当成发音错误。

### 强度缺席时标出来，但不声称强度

`errorType === "Monotone"` 而 `monotone` 字段缺席，意味着「知道读平了，
不知道多平」。这时画最轻的一档下划线，`intensity` 记 `null`——
**不编一个中间值**。编一个 0.5 出来，用户看到的是一条我们没测过的信息。
这和 [C43]「缺席用字段不出现表达，绝不发 null」是同一条纪律。

### 分档切点

`monotone` 是 0–1 连续量，映射成三档：`≤ 1/3` 轻、`≤ 2/3` 中、`> 2/3` 重。
三档而不是连续色阶的理由和 0019 的分档一样：**连续量在界面上会被当成精度**。
一条粗一点的下划线不会让人以为「0.62 和 0.64 有区别」，一个色阶会。

准确度低于 60 分即使 `errorType` 是 `None` 也按念错标——这条沿用现有界面里
那个 `LOW_ACCURACY` 常量，只是从 `index.html` 挪进了 `present.js` 的纯函数里。
