产品定位已更正 ACCURACY FIRST

准确度是主打。说话首先要说准。音念错了，再流利、语调再自然也是错的；音念准了，流利和语调才是在这之上的加分项。

此前这份路线图写的是「语调可以做主打」，理由是它的相关系数最高、校准偏差最小。那个理由混淆了两件事——「测得准不准」是评分服务的属性，「值不值得当主打」是产品判断。语调的测量质量最好这个事实不变，但测得最准的维度不等于最该突出的维度。一个能精确告诉你「语调略平」却不告诉你「这三个音念错了」的产品，把用户的注意力引到了次要的地方。

准确度Primary
排第一并高亮。逐词标红念错的音，悬停显示音素级明细——「第 3 个词的 /θ/ 念成了 /s/」才是能拿去改的东西，一个总分做不到。
流利度Supporting
第二位，只展示分档。
语调Supporting
第三位。逐词标黄读得平的词，但被标红盖过——一个词两样都占时先报念错。把音念对是基础。
完整度Hidden
不展示。朗读场景专家全给满分，没有区分度，而服务端平均只给 86.7，展示它只会制造无意义的焦虑。存库但不进界面。
这个改动让「不展示原始百分数」更要紧，不是更宽松关键

准确度的排序可信（斯皮尔曼 0.776，强相关，足以支撑趋势曲线），但绝对值虚高约 20 分——专家均分 65.8，服务端给 85.7。

主打维度报一个虚高的数字，整个产品的可信度就没了——用户以为自己念得很准，实际不是。所以「只展示分档不展示原始百分数」这条规则因为这次改动而更加必须遵守，分档切点仍用效度测量的数据反推。

语调仍然保留，理由变了差异化

不再是「主打」，而是两条：它是竞品缺口——参考实现 Enjoy 从没调用 enableProsodyAssessment，它数据库里的 prosodyScore 那一列永远是空的；它测得最准，适合放在趋势曲线上看长期变化——准确度改善要几周，语调的变化几天就看得出。

踩过的坑：第一次按顺序取前 20 条，相关系数全部低于 0.3，看着就是「服务不准，该换供应商」。查下来是取值范围压扁——那 20 条的专家分只有四个取值，完整度更是全部满分、方差为零。改成按分数分层抽样后结论完全反转。低相关先怀疑样本，再怀疑被测对象。

v0.2.0 修掉的三个 bug ALL CAUGHT BY TESTS

静音修剪用均方根会被单次爆音击败测试抓的

一个 30000 的爆音落在 160 采样的窗口里，RMS 被拉到阈值的 23 倍——平方放大离群值，单次咔哒声足以让整段静音一点都掐不掉。改成按「窗口内超过阈值的采样占比」判断：爆音占 0.6%，语音占 99%。

上一轮列边缘情况清单时写的是「用窗口不用单点」——方向对，但没意识到窗口内用什么统计量同样关键。

请求体超限时掐断连接从 v0.1.0 就在

destroy() 会在响应发出之前掐断连接，客户端拿到的是 fetch failed 而不是 413——完全不知道是自己传太大了。这个 bug 在 JSON 那条路上一直存在，从来没被测到，因为没人真的用超大请求体打过它。

测试用例互相干扰测试自身

每个用例重启服务器来换 provider，单独跑通过、连起来跑就挂——server.close() 要等 keep-alive 连接释放。改成一次性起两台服务器 + 可替换的代理。

参考实现三处照抄不得 WHAT NOT TO COPY

录音这一段抄了参考实现三条（16kHz/16bit 配置、掐首尾静音、到点自动停），但它的参数照抄不得。

它的做法问题
结尾阈值 -100 dBFS换算成 16 位整数是 0.33 个量化单位——低于 1，意味着「恰好为 0」。任何底噪都掐不动，那一半等于白做
切在阈值交越点p / t / k 的起音是陡峭瞬态，切在交越点会削掉前沿，听感变闷、准确度分数下降。我们往前退 50ms
直接算绝对值有些麦克风的静音段绝对值恒定不为零，不去均值的话修剪完全失效且不报错

它的录音功能零测试——e2e 里连 record 这个词都没出现。原因是逻辑散在 provider、组件、主进程模型三处，每处都混着 IPC 和文件系统，一个测试都写不了。我们把不可测的部分压到最薄：浏览器层只负责「拿到采样」，转换、修剪、编码、状态迁移全在 core/，171 个用例覆盖。

本轮修掉的一个 bug THREE GAPS, ONE CORRUPTION

音频缓存会被永久写坏，而三个各自被归档为「可以缓一缓」的缺口，谁都没描述这件事。

F4 无 in-flight 去重
  → 两个并发的相同请求，各调一次 provider
  → 缓存键是请求哈希不是内容哈希，两段音频不保证逐字节相同
  → 并发 writeFile 到同一路径（先截断再写）→ 交错 → 坏 WAV
get() 只 stat 不校验内容
  → 坏文件被当成缓存命中
F8 无淘汰
  → 永远不会被替换掉

用户看到的是某一句话的音频永远是坏的：重启没用，也没有任何界面能清掉它。第二条触发路径是磁盘满——写到一半 ENOSPC，截断的文件留在那里。

修法：写临时文件再 rename()，同目录内的 rename 在 POSIX 上是原子的。验证方式：把修复临时撤回，三条并发用例立刻变红——测试抓不到 bug 就是摆设。这也让 F4 的归类第一次准确：在 put() 修好之前，它不只是「付两次钱」。
