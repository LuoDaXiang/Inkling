# 路线图

四个阶段，每个阶段结束时都是一个能用的完整软件，不是半成品。
当前在 **Stage 0**。

---

## 阶段划分

| 阶段 | 形态 | 新学到的东西 |
| --- | --- | --- |
| **Stage 0** | 单人可用，填自己的 key，数据全在本地 | 完整交付一个软件 |
| Stage 1 | 能装到别人电脑上（macOS / Windows） | 打包、签名、自动更新、崩溃上报 |
| Stage 2 | 可选账号，服务端只做多设备同步 | 不登录仍然全功能可用 |
| Stage 3 | 兑换码充值，不集成在线支付 | 额度与计费，绕开支付通道 |

Stage 1 的关键动作是**加入本地 TTS 引擎（Kokoro）**：别人不申请 Azure key 也能用。
Stage 0 不做，因为那时候省的是自己的钱，而拆掉一个已经测透的 provider 是纯亏损。

**Stage 2 之前必须查清一件事**：转售 API 额度是否违反 OpenAI / Azure 的服务条款。
这件事会倒推账号体系的设计——如果不能代付，Stage 3 就只能是「用户填自己的 key」，
那 Stage 2 的服务端根本不需要计费能力，架构会简单一大截。

这个数据集每条由 **5 位语言专家独立打分**取平均作真值，说话人是
**母语为普通话的英语学习者**——和本项目目标用户同一人群，五个维度

    npm run validity -- --n 150 --min-age 16

**137 条成人样本，分层覆盖专家总分 3–10 全段：**

| 维度 | 皮尔逊 | 斯皮尔曼 | 专家均分 | Azure 均分 | 判读 |
| --- | --- | --- | --- | --- | --- |
| 准确度 | 0.723 | 0.776 | 65.8 | 85.7 | 强 |
| 流利度 | 0.758 | 0.808 | 69.9 | 86.7 | 强 |
| **语调** | **0.880** | **0.908** | 66.1 | **66.6** | **强** |
| 完整度 | — | — | 100.0 | 86.7 | 无方差 |
| 总分 | 0.815 | 0.869 | 61.2 | 78.3 | 强 |

**结论：Azure 这条路成立，不用换 Speechace。**
而且最想要的语调维度相关性最高（0.908），校准偏差也最小。

三条产品约束由此确定，详见 decisions 0019：
① 语调可以做主打 ② 准确度和流利度偏高约 20 分，界面不展示原始百分数
③ 完整度无区分度，存库但不展示。

**踩过的坑**：第一次按顺序取前 20 条，相关系数全部低于 0.3，看着像
「Azure 不准」——其实是取值范围压扁（专家分只有 7/8/9/10 四个取值，
completeness 全部满分）。改成分层抽样后结论完全反转。
**低相关先怀疑样本，再怀疑被测对象。**

**仍然建议你自己录两段**（认真读 / 故意平读）跑一次：数据集告诉你 Azure
在普通话母语者这个群体上准不准，你的录音告诉你它在**你**身上准不准。
这件事等 M03 录音做完顺手就能做，不阻塞。

测试验证的是代码符合预期，这一步验证的是**预期本身是否成立**。321 个用例教不了这件事。

### M03 — 浏览器录音与回放

| | |
| --- | --- |
| **交付** | AudioWorklet 采 16kHz 单声道 PCM，复用 `makeWav()` 拼 WAV，能录能放能对比听 |
| **验收** | 录下来的 wav 丢给 `parseWav()`，sampleRate 是 16000、channels 是 1 |
| **学到** | 浏览器媒体权限与音频管线 |

**这里有个坑**：Chrome 的 `MediaRecorder` 只产出 WebM 容器 + Opus 编码，
而 Azure 只接受 WAV（PCM 16-bit / 16kHz / 单声道）或 OGG（OPUS / 16kHz / 单声道）。
编码对得上但容器不对，直接上传必然被拒。

正确做法是绕开 `MediaRecorder`：`new AudioContext({ sampleRate: 16000 })` 加 AudioWorklet
拿原始 Float32 采样，转 Int16，自己拼 WAV 头。

**更正一处此前的说法**：`src/core/audio/wav.ts` 里那个函数叫 `buildWav`，
而且**只能产静音，不接受采样数据**——它是给测试造 WAV 头用的，不是编码器。
浏览器录音需要另写一个真能吃 Int16 采样的编码器，约 20 行，也放进 `core/audio/`，
这样 Node 侧和浏览器侧共用同一份。

### M04 — 评分服务层

| | |
| --- | --- |
| **交付** | 评分 provider 与 `azure.ts` 同构；`errors` 搬到 `core/` 改名 `ServiceError`；`assertAssessable()`；provider 接口加 `maxSeconds` |
| **验收** | 闭环跑通并显示三项分数；**errors 搬家后原有 321 个用例一个不红** |
| **学到** | 抽象的复用边界 + 重构的安全网 |

发音评估的 prosody **可以走 REST**：把配置 JSON 做 base64 后放进 `Pronunciation-Assessment`
请求头，字段写 `"EnableProsodyAssessment": "True"`。所以评分 provider 可以和 `azure.ts`
完全同构——继续用 `FetchLike`，继续用 `fakeFetch`，**不引入任何运行时依赖**。

**送出请求前必须自己挡住的输入**（全部实测过，见 decisions 0020）：

| 必须挡 | 不挡的后果 |
| --- | --- |
| 空参考文本 | 触发无参考评估，**返回一个看起来正常的高分**，不报错 |
| 超长参考文本 | 服务端不返回响应头，**请求挂死**（实测约 13000 字符） |
| 音频超约 35 秒 | **不是硬拒绝，是静默截断**。73 秒音频完整度只给 49（≈35/73），状态仍是 Success。用户完整读完却看到完整度腰斩 |
| 无声 / 空音频 | 返回 200 但没有 `NBest`，**光看状态码会当成成功** |

**解析响应时必须防住的**：
- `RecognitionStatus` 可能整个字段都不存在 → 判断顺序是先看 `NBest?.[0]`
- `ProsodyScore` 可能缺席（音频截断、参考无效时）→ 类型是 `number | undefined`
- 五项分数是小数不是整数；`ProsodyScore` 实测从不给 100
- 单个维度不能单独信——纯白噪声的准确度是 71 分，靠流利度 13 和总分 32.7 才看得出不对
- fetch 必须设显式超时，否则一个坏输入能把请求链挂住

这是项目第一次真正改动已有代码，CI 和 321 个测试在这一步第一次兑现价值。

## 已核实与未核实

写下来是为了以后回头时知道哪些是查过的、哪些是估的。

**已核实（官方文档）**

- 发音评估的 prosody 支持 REST，经 base64 的 `Pronunciation-Assessment` 头传 `EnableProsodyAssessment`（**已用真实调用验证**）
- 评估音频须 WAV / PCM 16-bit / 16kHz / 单声道，或 OGG / OPUS / 16kHz / 单声道
- 单次评估音频不超过 30 秒
- Prosody 仅支持 `en-US`——正好是本项目唯一的目标语言，此限制不构成约束
- Chrome 的 `MediaRecorder` 只产 WebM 容器，Azure 不接受

**未核实**

- 转售 API 额度是否违反服务条款（Stage 2 之前必须查清）
- 所有工时估算
