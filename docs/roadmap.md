# 路线图

四个阶段，每个阶段结束时都是一个能用的完整软件，不是半成品。
当前在 **Stage 0**。

---

## 阶段划分

| 阶段 | 形态 | 新学到的东西 |
| --- | --- | --- |
| **Stage 0** | 单人可用，填自己的 key，数据全在本地 | 完整交付一个软件 |
| Stage 1 | 能装到别人电脑上（macOS / Windows） | 打包、签名、自动更新、崩溃上报 |
| Stage 2 | 可选账号，服务端只做多设备同步 | 不登录仍然全功能可用 |
| Stage 3 | 兑换码充值，不集成在线支付 | 额度与计费，绕开支付通道 |

Stage 1 的关键动作是**加入本地 TTS 引擎（Kokoro）**：别人不申请 Azure key 也能用。
Stage 0 不做，因为那时候省的是自己的钱，而拆掉一个已经测透的 provider 是纯亏损。

**Stage 2 之前必须查清一件事**：转售 API 额度是否违反 OpenAI / Azure 的服务条款。
这件事会倒推账号体系的设计——如果不能代付，Stage 3 就只能是「用户填自己的 key」，
那 Stage 2 的服务端根本不需要计费能力，架构会简单一大截。

### M01 — 让它变成一个能打开的东西　🔨 进行中

| | |
| --- | --- |
| **交付** | 配 key 跑通 live；`node:http` 服务；一个页面：输入框 + 按钮 + 播放器；CI |

live 一跑，37 个假 fetch 用例才第一次见到真实响应。

### M02 — 评分效度测量　（2 小时，跑完可删）

| | |
| --- | --- |
| **交付** | 五段音频跑一遍 Azure 发音评估，打印四项分数对照表 |
| **验收** | 先凭耳朵排序写下来，**再**看机器排序 |
| **学到** | 区分「能跑通」和「值得信」 |

五段音频：① 认真读，带抑扬顿挫 ② 故意平读，全程一个调 ③ 故意读快，吞音
④ 母语者原声 ⑤ 本项目 TTS 合成音。

**判据**：两个排序一致 → 继续。①②的 Prosody 分数拉不开 → 停下，换 Speechace 用同样五段重测，选型重议。

第 ⑤ 段是最值得看的对照：如果机器给自己合成的音打满分、给母语者真人录音打低分，
说明这个模型偏爱合成语音的规整度，用它给人打分会**系统性惩罚自然口语**——
那这条路对跟读产品就是错的，再「准」也不能用。

测试验证的是代码符合预期，这一步验证的是**预期本身是否成立**。321 个用例教不了这件事。

### M03 — 浏览器录音与回放

| | |
| --- | --- |
| **交付** | AudioWorklet 采 16kHz 单声道 PCM，复用 `makeWav()` 拼 WAV，能录能放能对比听 |
| **验收** | 录下来的 wav 丢给 `parseWav()`，sampleRate 是 16000、channels 是 1 |
| **学到** | 浏览器媒体权限与音频管线 |

**这里有个坑**：Chrome 的 `MediaRecorder` 只产出 WebM 容器 + Opus 编码，
而 Azure 只接受 WAV（PCM 16-bit / 16kHz / 单声道）或 OGG（OPUS / 16kHz / 单声道）。
编码对得上但容器不对，直接上传必然被拒。

正确做法是绕开 `MediaRecorder`：`new AudioContext({ sampleRate: 16000 })` 加 AudioWorklet
拿原始 Float32 采样，转 Int16，自己拼 WAV 头。

而 `makeWav()` 已经写好了（`src/core/audio/wav.ts`），纯函数，浏览器里能直接跑——
当初为造测试数据写的东西，恰好是录音链路缺的那一块。

### M04 — 评分服务层

| | |
| --- | --- |
| **交付** | 评分 provider 与 `azure.ts` 同构；`errors` 搬到 `core/` 改名 `ServiceError`；`assertAssessable()`；provider 接口加 `maxSeconds` |
| **验收** | 闭环跑通并显示三项分数；**errors 搬家后原有 321 个用例一个不红** |
| **学到** | 抽象的复用边界 + 重构的安全网 |

发音评估的 prosody **可以走 REST**：把配置 JSON 做 base64 后放进 `Pronunciation-Assessment`
请求头，字段写 `"EnableProsodyAssessment": "True"`。所以评分 provider 可以和 `azure.ts`
完全同构——继续用 `FetchLike`，继续用 `fakeFetch`，**不引入任何运行时依赖**。

两个新约束，现有代码都不知道：
- 音频必须 WAV / PCM 16-bit / 16kHz / 单声道
- 单次评分音频**不超过 30 秒**——现在的上限是 3000 **字符**，字符数不等于时长

这是项目第一次真正改动已有代码，CI 和 321 个测试在这一步第一次兑现价值。

### M05 — SQLite 与操作流水

| | |
| --- | --- |
| **交付** | `material → sentence → recording → assessment` 四张表，**外加一张 `operations` 流水表** |
| **验收** | 改一次表结构后重跑，老记录不丢；能查出「上周练了几次、失败几次、花了多少」 |
| **学到** | 数据模型与迁移 |

流水表每次 TTS 和评分记一行：时间、输入、耗时、花费、成败。

代码写烂了一周能重构，**数据模型定错了、里面还存着半年的记录，那是真的难改**。
流水现在不留，以后补不回来——过去的数据不会重新产生。

### M06 — AI 生成与导入

| | |
| --- | --- |
| **交付** | Claude API 按体裁生成（口语对话 / 播客独白 / 新闻），**外加自己粘贴导入** |
| **验收** | 连开十次不重复，没有一句读起来像教科书 |
| **学到** | 提示词当代码管——进版本库、能回滚、能 A/B |

「地道」的关键在 prompt 里的体裁和场景约束，不在模型。
生成层直接复用现成的 `errors` 和缓存，前面分层的回报在这里兑现。

### M07 — 还测试债

| | |
| --- | --- |
| **交付** | 并发去重、变异测试、响应 fixture、property-based、缓存上界 |
| **验收** | 四个纯函数模块**变异分数超过 80%** |
| **学到** | 用工具评判测试，而不是数用例个数 |

具体条目见下方「已知缺口」。

**为什么排在最后**：这些债都不阻塞任何后续步骤，而当前最大的缺口是
「没有完整交付过一个软件」。先把闭环走通拿到那个经验，再回头夯地基。

注意这和「纯逻辑要立刻测」不矛盾——纯逻辑的测试早就写了（M00 就做完了），
往后放的是**测试的精修**，那需要有东西可保护时才有意义。

## 已核实与未核实

写下来是为了以后回头时知道哪些是查过的、哪些是估的。

**已核实（官方文档）**

- 发音评估的 prosody 支持 REST，经 base64 的 `Pronunciation-Assessment` 头传 `EnableProsodyAssessment`
- 评估音频须 WAV / PCM 16-bit / 16kHz / 单声道，或 OGG / OPUS / 16kHz / 单声道
- 单次评估音频不超过 30 秒
- Prosody 仅支持 `en-US`——正好是本项目唯一的目标语言，此限制不构成约束
- Chrome 的 `MediaRecorder` 只产 WebM 容器，Azure 不接受

**未核实**

- 转售 API 额度是否违反服务条款（Stage 2 之前必须查清）
- 评分 REST 端点的完整 URL 路径（第一次 live 调用时以实际响应为准）
- 所有工时估算
