# 路线图

四个阶段，每个阶段结束时都是一个能用的完整软件，不是半成品。
当前在 **Stage 0**，版本 **v0.2.0**。

---

## 阶段划分

| 阶段 | 形态 | 新学到的东西 |
| --- | --- | --- |
| **Stage 0** | 单人可用，填自己的 key，数据全在本地 | 完整交付一个软件 |
| Stage 1 | 能装到别人电脑上（macOS / Windows） | 打包、签名、自动更新、崩溃上报 |
| Stage 2 | 可选账号，服务端只做多设备同步 | 不登录仍然全功能可用 |
| Stage 3 | 兑换码充值，不集成在线支付 | 额度与计费，绕开支付通道 |

Stage 1 的关键动作是**加入本地 TTS 引擎（Kokoro）**：别人不申请 Azure key 也能用。
Stage 0 不做，因为那时候省的是自己的钱，而拆掉一个已经测透的 provider 是纯亏损。

**Stage 2 之前必须查清一件事**：转售 API 额度是否违反 OpenAI / Azure 的服务条款。
这件事会倒推账号体系的设计——如果不能代付，Stage 3 就只能是「用户填自己的 key」，
那 Stage 2 的服务端根本不需要计费能力，架构会简单一大截。

### M02 — 评分效度测量　✅

原计划是自己录五段凭耳朵排序。改用 `speechocean762` 公开基准：
每条由 **5 位语言专家独立打分**取平均作真值，说话人是母语为普通话的
英语学习者——和目标用户同一人群，五个维度与 Azure 返回的一一对应。

    npm run validity -- --n 150 --min-age 16

**137 条成人样本，分层覆盖专家总分 3–10 全段：**

| 维度 | 皮尔逊 | 斯皮尔曼 | 专家均分 | Azure 均分 | 判读 |
| --- | --- | --- | --- | --- | --- |
| 准确度 | 0.723 | 0.776 | 65.8 | 85.7 | 强 |
| 流利度 | 0.758 | 0.808 | 69.9 | 86.7 | 强 |
| **语调** | **0.880** | **0.908** | 66.1 | **66.6** | **强** |
| 完整度 | — | — | 100.0 | 86.7 | 无方差 |
| 总分 | 0.815 | 0.869 | 61.2 | 78.3 | 强 |

**Azure 这条路成立，不用换 Speechace。** 四个维度的相关系数都在 0.776 以上，
足以支撑趋势曲线和「这次比上次好吗」。三条产品约束由此确定：

1. **界面不展示原始百分数** —— 准确度和流利度系统性偏高约 20 分（decisions 0019）
2. **完整度不展示** —— 朗读场景无区分度，存库但不进界面
3. **语调分擅长挑出差的，分不出好和更好** —— 高分段不显示细微差别（decisions 0021）

**注意一处曾经的混淆**（已在 decisions 0035 更正）：语调的相关系数最高、
校准偏差最小，这是**测量质量**好；一度被当成「所以语调该做主打」，
那是把测得准和值得突出这两件事混为一谈了。产品定位见下方「三个维度的分工」。

另外：语调分**擅长挑出差的，分不出好和更好**。专家 3 分对 Azure 22.5，
专家 10 分对 88.6，单调递增；但 8/9/10 三档压在 84.7/86.9/88.6，只差 4 分。
高分段界面不该再显示细微差别，把注意力引导到逐词明细上。

## 三个维度的分工

**准确度是主打。说话首先要说准。** 音念错了，再流利、语调再自然也是错的；
音念准了，流利和语调才是在这之上的加分项。见 decisions 0035。

| 维度 | 角色 | 界面上怎么呈现 |
| --- | --- | --- |
| **准确度** | **主打** | 排第一并高亮；逐词标红；悬停看音素级明细 |
| 流利度 | 辅助 | 第二位，只展示分档 |
| 语调 | 辅助 | 第三位；逐词标黄，被标红盖过 |
| 完整度 | 不展示 | 存库但不进界面 |

**这个定位让「不展示原始百分数」更要紧**，不是更宽松：准确度的绝对值
虚高约 20 分（专家 65.8 对服务端 85.7），而主打维度报一个虚高的数字，
整个产品的可信度就没了。

**语调仍然保留**，理由从「主打」改成两条：它是竞品缺口（参考实现从没调用
`enableProsodyAssessment`，那一列永远是空的）；它测得最准，
适合放在趋势曲线上看长期变化——准确度改善要几周，语调的变化几天就看得出。

**踩过的坑**：第一次按顺序取前 20 条，相关系数全部低于 0.3，看着像
「Azure 不准」——其实是取值范围压扁（专家分只有四个取值，完整度全是满分）。
改成分层抽样后结论完全反转。**低相关先怀疑样本，再怀疑被测对象。**

### M04 — 评分服务层　✅

| 子块 | 状态 | 内容 |
| --- | --- | --- |
| `parse.ts` | ✅ 62 用例 | 响应解析。语句/分支/函数/行全 100% |
| `config.ts` | ✅ 44 用例 | `Pronunciation-Assessment` 请求头。全 100% |
| `azure.ts` | ✅ 52 用例 | provider + 假 fetch。全 100% |
| `assess.ts` | ✅ 31 用例 | 编排层。三种走向、带重试 |

**送出请求前必须自己挡住的**（全部实测，见 decisions 0020、0022）：

| 必须挡 | 不挡的后果 | 状态 |
| --- | --- | --- |
| 空参考文本 | 触发无参考评估，**返回看起来正常的高分**，不报错 | ✅ `prepareReference` |
| 超长参考文本 | 编码后超请求头上限，**请求挂死**而非 4xx | ✅ 上限由音频上限推导 |
| 音频超约 35 秒 | **静默截断**。73 秒音频完整度只给 49（≈35/73），状态仍是 Success | ✅ `assertAssessable` |
| 无声 / 空音频 | 返回 200 但没有 `NBest`，**光看状态码会当成成功** | ✅ `parseAssessment` 返回 null |

**解析响应时必须防住的**（已全部实现并有用例）：

- `RecognitionStatus` 可能整个字段都不存在 → 判断顺序是先看 `NBest?.[0]`
- `ProsodyScore` 可能缺席 → 类型是 `number | undefined`
- 五项分数是小数不是整数；`ProsodyScore` 实测从不给 100
- **单个维度不能单独信**——纯白噪声准确度 71 分，靠流利度 13 和总分 32.7
  才看得出不对 → `looksLikeSpeech()` 看组合

**已补齐的防护**：所有 `fetch` 调用都带显式超时（`fetchWithTimeout`）；
429 读 `Retry-After`；错误带上 `RequestId`。

**评分结果分三种走向**，调用方必须全处理——`scored` / `unreliable` / `no_speech`。
`unreliable` 的判据来自实测：纯白噪声准确度 71 分，单个维度不能单独信。
见 decisions 0027。

### M03 — 浏览器录音与回放　✅　`v0.2.0`

| | |
| --- | --- |
| **交付** | AudioWorklet 采 16kHz 单声道 PCM，编码成 WAV，能录能放能对比听 |
| **验收** | 录下来的 wav 丢给 `parseWav()`，sampleRate 是 16000、channels 是 1 |
| **学到** | 浏览器媒体权限与音频管线 |

**坑一**：Chrome 的 `MediaRecorder` 只产出 WebM 容器 + Opus 编码，
而 Azure 只接受 WAV 或 OGG。编码对得上但容器不对，直接上传必然被拒。
正确做法是绕开它：`new AudioContext({ sampleRate: 16000 })` 加 AudioWorklet
拿原始 Float32 采样，转 Int16，自己拼 WAV 头。

**坑二**：`src/core/audio/wav.ts` 里的 `buildWav` **只能产静音，不接受采样数据**——
它是给测试造 WAV 头用的，不是编码器。需要另写一个真能吃 Int16 采样的编码器，
约 20 行，同样放进 `core/audio/`，让 Node 侧和浏览器侧共用一份。

**坑三**：请求体上限已经拆成 `MAX_JSON_BYTES` / `MAX_AUDIO_BYTES`，
录音路由必须用后者。用错就会拒掉任何超过两秒的录音。

**坑四**：用户点「录音」到真正开口总有一两秒空白，读完到点「停止」也一样。
**这段静音会拉低流利度分数，而它和发音水平毫无关系。**
参考实现在落盘前掐掉首尾静音（开头 -50dB，结尾 -100dB，开头更宽松
因为一开口就有声音）。这条我原先没想到，见 decisions 0030。

**分层纪律**（这是参考实现做不到的）：

```
core/audio/encode-wav.ts     Int16Array → WAV 字节   纯函数，可测
core/audio/trim-silence.ts   掐首尾静音              纯函数，可测
public/recorder.js           AudioWorklet + 权限      不可测，尽量薄
```

浏览器那层只负责「拿到采样」，别的什么都不做。Enjoy 的录音逻辑散在
provider、组件、主进程模型三处，每处都混着 IPC 和文件系统，**一个测试
都写不了**——它的录音功能确实零测试。

**顺带做掉**：录一段自己认真读的、一段故意平读的，跑一遍评分。
数据集告诉我们 Azure 在普通话母语者这个群体上准不准，这两段告诉我们
它在**你**身上准不准。不阻塞任何事，但值得做。

### M05 — SQLite 与操作流水　🔨

| | |
| --- | --- |
| **交付** | `material → sentence → recording → assessment` 四张表，**外加一张 `operations` 流水表** |
| **验收** | 改一次表结构后重跑，老记录不丢；能查出「上周练了几次、失败几次、花了多少」 |
| **学到** | 数据模型与迁移 |

流水表每次 TTS 和评分记一行：时间、输入、耗时、花费、成败。

代码写烂了一周能重构，**数据模型定错了、里面还存着半年的记录，那是真的难改**。
流水现在不留，以后补不回来——过去的数据不会重新产生。

**评分结果的表要为逐词明细留位置**：`Words[]` 里的**音素级准确度**是主打
维度的落脚点——「第 3 个词的 /θ/ 念成了 /s/」才是能拿去改的东西，
一个总分做不到。`monotone` 和 `breakError` 一并存下，它们是语调那一侧的明细。

**趋势曲线以准确度为主线**，流利度和语调作对照。准确度的绝对值虚高约 20 分，
所以曲线画的是**相对变化**而不是原始分数——用户要看的是「我在变好吗」，
不是「我今天得了 85 分」。

## 已核实与未核实

写下来是为了以后回头时知道哪些是查过的、哪些是估的。

### 已核实（真实调用验证过）

**接口形状**

- prosody 走 REST 可用，经 base64 的 `Pronunciation-Assessment` 头传 `EnableProsodyAssessment`
- **REST 的响应比 SDK 扁一层**：五项分数直接挂在 `NBest[0]` 上，不在
  `PronunciationAssessment` 子对象里。照 SDK 的字段路径取会全部拿到 `undefined` 且不报错
- 每个词带 `Feedback.Prosody`，含单调检测 `Monotone` 与停顿检测 `Break`
- 响应顶层有 `SNR`（实测 38.7），可用于提示「麦克风太吵」
- Prosody 仅支持 `en-US`——正好是本项目唯一的目标语言

**失败行为**

- **HTTP 一律 200**，失败信息藏在 `RecognitionStatus` 里
- 空音频时**连 `RecognitionStatus` 字段本身都不存在**
- 空参考文本 → 触发无参考评估，返回总分 92.2 的高分，不报错
- 约 13000 字符的参考文本 → 服务端不返回响应头，**请求挂死**
- 超约 35 秒的音频 → **静默截断**，完整度按比例下降，状态仍是 Success
- 纯白噪声 → `Success`，准确度 71，靠流利度 13 和总分 32.7 才看得出不对

**格式宽容度（推翻了此前的判断）**

- Azure **不强制**单声道：立体声分数与单声道完全一致
- Azure **不强制** 16kHz：8kHz 分数几乎无差
- Azure **忽略** `Content-Type` 里的采样率声明，自己读 WAV 头
- 带 `LIST` 块的 WAV 照收——**我们的 `parseWav` 曾经比 Azure 还严格**

**跨层常量分叉（本机变异测试实测）**

- 单独改服务端的 `RECORDING_SAMPLE_RATE` → **2 条测试红**；
  单独改 `MAX_ASSESSABLE_SECONDS` → **8 条红**，散在 6 个文件里
- 但那些既有断言**全都是「服务端常量 == 字面量」或服务端两个常量互相对账，
  没有一条看过客户端**。真正没人守的是反方向：改客户端那份 16000，全绿——
  而那恰恰是更容易发生的方向，改前端的人不会去跑服务端测试
- `tests/contract-consistency.test.ts` 补的就是这个方向。它 import
  `public/recorder.js` 的真实导出，值只从 HTTP 响应取，并有一条自检用例
  读自己的源码防止将来有人 import 服务端常量把它退化成自己等于自己

**SQLite 与 `node:sqlite`（本机实测，Node v22.22.3 / SQLite 3.51.3）**

- **pragma 顺序有影响**：`journal_mode=WAL` 排在 `auto_vacuum` 前面，会让
  auto_vacuum 静默停留在 0（不报错）。反过来才是 2。WAL 写数据库头，头一写下就焊死
- **DELETE 不还空间**：删掉 4000 行流水，`.db` 文件大小**一个字节不变**；
  `incremental_vacuum` 之后缩到不足一半
- `STRICT` 表确实拒绝类型错误：`cannot store TEXT value in INTEGER column`
- 双引号字符串字面量在这个构建里是**关的**——列名打错会报 `no such column`，不会静默变成常量
- **布尔绑定直接抛** `Provided value cannot be bound`。Node main 的
  `test-sqlite-data-types.js` 里 `true` 会转成 1——**上游文档和本机运行时不一致**
- `undefined` 绑定抛 `ERR_INVALID_ARG_TYPE`；TypeScript 也在编译期就拒绝
- 超过 2^53 的整数读回来抛 `too large`，要显式 `setReadBigInts(true)`
- 返回的行对象是 **null 原型**，外部 JSON 里的 `__proto__` 不会污染原型链
- `node:sqlite` **不在 `module.builtinModules` 里**（但 `isBuiltin` 返回 true），
  这正是 Vite 解析不了它的原因（0036）
- `BEGIN IMMEDIATE` 可以造出确定性的写锁竞争，不必靠 sleep 碰运气
- 优雅关闭（SIGTERM → `db.close()`）会 checkpoint 掉 `-wal` 和 `-shm`，只剩一个自包含的 `.db`

**其他**

- 评分**完全确定性**：同一段音频评三次，五项分数一字不差。趋势曲线有意义
- Chrome 的 `MediaRecorder` 只产 WebM 容器，Azure 不接受
- Azure TTS **造不出「读得平」的语音**：SSML 的 `contour` 压平被忽略
  （合成音频字节与默认完全相同），`express-as` 的 `cheerful` 在
  `en-US-AvaNeural` 上同样无效。受控语调实验这条路走不通

### 未核实

- 转售 API 额度是否违反服务条款（**Stage 2 之前必须查清**，会倒推账号体系设计）
- 429 限流的实际行为与 `Retry-After` 头（退避代码写了但从没执行过）
- 免费额度 F0 耗尽时返回什么
- 并发上限（效度脚本是串行的，137 条跑了 10 分钟）
- `NBest` 何时会多于一条（一直假设取 `[0]`）
- 儿童样本的相关性（效度测量筛掉了 1280 条）
- 效度测量只有一个种子、n=137，没有置信区间
- 麦克风回声：用户外放范本时可能把 TTS 录进去
- **流水写入在真实并发下的延迟**：`node:sqlite` 是同步 API，会阻塞事件循环。
  单行 INSERT 到 WAL 通常在微秒级，但**没有实测过**
- **`operations` 的实际增长速率**，因此保留窗口该设多长也没有依据
- **失败的调用到底计不计费**：现在的实现假设「重试后成功只计一次」，
  因为失败的尝试通常不计费。**没有拿真实账单核对过**
- **费率本身**：`.env.example` 里的数量级仅供参考，必须按自己的 Azure
  定价页和账单核对。费率错了不会有任何东西报错
- **`phoneme_score` 在真实数据量下的查询性能**：一句 10 词 × 每词约 3 音素
  = 每次录音 30+ 行，练一年是几十万行。建了索引，但没有压过
- 所有工时估算
